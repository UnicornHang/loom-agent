# Loom 项目架构与目录约定

> 状态：基础层开发中。此文件描述目标目录及当前实现状态，不能把目录占位视为功能完成。

## 1. 总体架构

采用模块化单体：浏览器中的 React 工作台调用 FastAPI；FastAPI 负责身份、权限、业务事务和查询；长任务由采集、Agent、媒体 Worker 执行。PostgreSQL 保存产品事实、权限、工作流和版本，pgvector 仅做检索索引；Redis 承载队列；对象存储保存媒体。Agent 使用 LangGraph 编排与人工确认，节点之间传结构化产物引用。每次 Agent 执行写入可核验的事件，再推送给前端。

当前 React 工作台、FastAPI 基础接口可以运行；本地非容器模式默认使用 SQLite。项目根目录的 `compose.yaml` 已提供开发容器，启动前端、API、PostgreSQL + pgvector、Redis 与 MinIO。Redis 和 MinIO 尚未接入业务功能，其他组件按下述边界逐步接入。

## 2. 目录

```text
loom-agent/
├─ README.md                 项目入口、启动方式、已实现范围
├─ docs/                     PRD、技术方案、目录约定；后续规范和手册
├─ frontend/                 React + TypeScript + Vite
│  ├─ src/App.tsx             当前工作台页面，后续逐步拆到 features
│  ├─ src/api.ts              当前 API 客户端，后续从 OpenAPI 生成
│  └─ src/features/           未来按业务域组织页面与组件
├─ backend/                  FastAPI 服务和 Python 任务
│  ├─ app/main.py             应用组装与开发启动保护
│  ├─ app/api/v1/routes/      HTTP 入口：登录、账号、授权、热点、产品、工作流
│  ├─ app/security.py         密码哈希、会话及请求校验

│  ├─ app/agents/             Agent 类型、交接与可见事件契约
│  ├─ app/collectors/         获准来源的 SourceAdapter 契约
│  ├─ app/services/           业务规则：权限、推荐、版本、确认等
│  ├─ app/integrations/       模型、MCP、存储与外部来源适配
│  ├─ app/workers/            采集、Agent、媒体异步任务
│  ├─ app/models.py           当前开发期 ORM；后续按领域拆分
│  ├─ app/schemas.py          当前 API Schema；后续按领域拆分
│  ├─ migrations/             版本化数据库迁移
```

空模块仅作为扩展边界。添加功能时应同时交付代码、权限校验、必要测试与运行说明，不以创建文件夹代替实现。

## 3. 模块依赖方向

`API → 业务服务 → 数据库/集成`。采集器与 Agent Worker 调用业务服务，不能直接绕过授权修改其他领域的数据。外部来源、MCP 返回和用户上传素材均按非可信输入处理。

- `api/v1/routes`：校验输入、认证上下文、HTTP 状态和响应；不放推荐公式或 Agent 推理逻辑。
- `services`：产品可见范围、热点入选、推荐评分、版本提交和人工确认等业务规则。
- `agents`：LangGraph 图、节点、Skill 选择和 Agent 间交接。图状态只存小型状态与产物 ID。
- `collectors`：每个允许自动访问的来源单独实现适配器；统一字段、游标、限流、去重和采集证据。
- `integrations`：供应商 SDK、对象存储、MCP 工具网关；负责超时、重试和错误映射。
- `workers`：异步执行、幂等与重试，完成后持久化事件和产物版本。

## 4. 前端分层

下一步从 `App.tsx` 拆出 `features/hotspots`、`features/workflows`、`features/products`、`features/content`、`features/agents`、`features/settings`，通用布局和控件进入 `components`，API 类型由 OpenAPI 生成。工作流页包含节点时间线、内容编辑区、操作区与每个 Agent 的执行记录。可见“思考过程”是阶段、证据、真实工具调用、草稿版本和自检摘要，不伪造模型内部推理。

## 5. 实施顺序与完成定义

1. **基础层**：账号、权限、产品授权、PostgreSQL/Alembic、对象存储。完成时无权产品在 API、搜索、素材和 Agent 上下文均不可见。
2. **Agent 底座**：LangGraph、模型连接、Skill/MCP 边界、任务队列、outbox、产物版本、人工确认和事件流。完成时重试幂等、断点恢复和事件回放可验证。
3. **图文闭环**：素材上传、分析、混合推荐、三稿、局部编辑、美工、按需审核、内容库与下载。
4. **视频首期**：剧本、逐镜分镜、局部调整和导出；不包含成片生成。
5. **自动采集**：仅接允许自动访问且已确认字段范围的来源；两周试采后评估覆盖和质量。

当前已加入产品素材、独立 Agent 配置、Skill 库、MCP 只读发现、预算、LangGraph 创作子图、Celery/outbox、内容版本与人工确认、局部修改、按需文本审核、图文/剧本/分镜导出、混合推荐和来源预检调度。真实模型及采集尚待配置与授权；自动美工、工具执行、完整外层图和生产加固仍未完成。具体证据及边界见《开发进度与验收记录.md》，上述 1–5 项尚未整体验收。

## 6. 文档存放规则

PRD 和技术方案统一放 `docs/`，项目入口仅在根 `README.md`。后续按需增加 `docs/api/`、`docs/decisions/`、`docs/operations/`；部署文件放 `infra/`，不混入方案文档。修改跨模块设计时同步更新技术方案和本目录约定。
